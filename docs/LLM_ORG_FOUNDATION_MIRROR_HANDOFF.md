## Goal

Establish the smallest non-duplicative organization-level foundation for a centralized, InTr-accessible multi-LLM / AI-entity ecosystem-construction environment. The foundation exists to let authorized work reconstruct the purpose and applicable cross-ecosystem contracts of the item being reviewed before repair or further construction.

This task does not create a second LLM provider broker, governance engine, route authority, credential authority, worker-claim authority, custody authority, Publisher path, or Ecosystem Chat runtime.

## Existing owners that are reused

- Task Registry: work-intent authority.
- WorkerCoordinator: worker claim/fence authority.
- Interlock/InTr: transition authority and organization-crossing packet/evidence path.
- StegVerse SDK: manifest construction, validation, declared capability/route semantics, and SDK return contracts.
- LLM-adapter: provider-neutral LLM access, named-source distributed workload, provider transport, contribution provenance, and packaging of evidence for existing governance.
- TV/TVC: credential/provider-operation and applicable route authority.
- Master Records: organization records/reconstruction.
- Publisher: governed publication/output continuation where applicable.

## New foundation responsibility

The new layer owns only:
1. canonical work-context resolution through InTr;
2. a provider/entity-neutral Sandbox collaboration object;
3. capability declarations sufficient to request an appropriate participating intelligence without granting it authority;
4. cross-ecosystem purpose reconstruction before a repair is evaluated when the component participates in cross-repository contracts;
5. evidence-preserving collaboration records that can be handed to existing governance.

Provider-specific repositories may describe provider/entity capabilities and interface constraints. They do not copy canonical ecosystem truth and do not become independent governance systems.

## Ecosystem AI boundary

The Ecosystem AI is not an LLM and is not an interpretive judge. Its governance function matches manifested claims and proposed transitions against admissible evidence and reconstructable receipted history.

It does not determine truth from appearance, consensus, reputation, model confidence, or majority vote.

Participating LLM/AI-entity outputs remain attributable candidate information/evidence and grant no governance, transition, route, credential, custody, publication, or execution authority.

## Inference Window

The Inference Window is the forward-looking component. It is disposition-complete.

For every disposition available in the applicable Admissibility Matrix:

> If this disposition is applied, what states or consequences might or might not become reachable?

The projection must retain the disposition, evidence basis, assumptions, uncertainty/conditions, and projected reachable/non-reachable consequences. A projection is not evidence that a consequence occurred. Only later admissible observation and receipted history may establish occurrence.

## Work-context rule

A repair to a component participating in cross-ecosystem contracts may not be evaluated solely against the repository being repaired. The work context must resolve the applicable canonical purpose and evidence, including relevant repository documentation, schemas, tests, Task Registry state, handoffs, manifests, receipts, Master Records references, and cross-repository contracts.

Resolution is relevance-bounded. The contract does not require copying the entire ecosystem into an LLM context window.

## Sandbox rule

The Sandbox coordinates bounded work objects rather than granting free-form authority. A work object binds:
- task/work identity;
- manifested problem/request;
- resolved canonical context references;
- permitted capabilities;
- participating entity identities;
- attributable candidate outputs;
- disagreements/refusals/uncertainty;
- tests/derived artifacts;
- evidence references;
- existing-governance handoff state.

## Explicit non-duplication

Existing LLM-adapter distributed workload already supports named-source single/parallel/sequential/challenge/fallback execution, contributor provenance, disagreement retention, and evidence packaging for existing governance. This foundation must consume/reuse those semantics rather than reimplement them.

## Secondary goal deferred

The consumer loop is not required to close this foundation task:

`Ecosystem Chat -> SDK Manifest Builder -> manifested LLM Org route -> governance -> Publisher -> SDK -> desired Ecosystem Chat output`.

That is a successor integration after the foundation contracts are canonical.

## Completion predicates

1. Task Registry and COSV projection are canonical.
2. Machine-readable work-context and Sandbox contracts exist.
3. Tests prove participating LLM/AI entities cannot acquire governance authority through these contracts.
4. Tests prove provider routing/transport is delegated to existing LLM-adapter surfaces rather than duplicated.
5. Tests prove disposition-complete Inference Window records distinguish projection from observed/receipted history.
6. README describes the new organization-level coordination responsibility and reuse boundaries.
7. Repository-required validation succeeds at exact head.
8. Merge uses expected-head protection.

No runtime activation, external provider execution, Publisher delivery, Ecosystem Chat delivery, or Master Records custody is claimed by source completion alone.
