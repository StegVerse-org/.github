## Purpose

This handoff records the organization-federation runtime repair required so any correctly registered `INTERNAL_ENDPOINT` service with an `endpoint_adapter` can be dispatched through the existing Interlock/InTr organization boundary without service-ID hardcoding.

The repair is provider-neutral and is not a Shared Docs-specific route. It is a prerequisite for a future generic WorkSpace receiver to use the already-existing service registry and federation dispatch architecture.

## Defect

`org-kernel/kernel.py::dispatch` already treats a registered service generically: for `boundary_role == INTERNAL_ENDPOINT` plus `endpoint_adapter`, it invokes `org-boundary/runtime/process_boundary.py`.

However, `org-boundary/runtime/process_boundary.py::endpoint_result` currently executes an adapter only when:

```text
service_id == stegverse-org.stegverse-sdk
AND endpoint_adapter is configured
```

Any other `INTERNAL_ENDPOINT` service with a valid registered adapter reaches `endpoint-adapter-not-installed`. This contradicts the registry-driven dispatch model and prevents adding a generic WorkSpace/internal endpoint without another hardcoded branch.

## Required repair

`process_boundary.py` must execute the configured `endpoint_adapter` for any registered `INTERNAL_ENDPOINT` service, while preserving these boundaries:

- destination organization and service must already match the local registry;
- only a registry-declared adapter may execute;
- adapter path must resolve within the organization repository root;
- missing/non-file adapters fail closed;
- adapter nonzero exit or missing output fails closed;
- boundary receipts remain generated by the boundary processor;
- adapter execution does not grant transport, credential, governance, or transition authority;
- diagnostic/control services retain their existing behavior.

## Validation predicates

Focused tests must prove:

1. the existing SDK endpoint adapter still executes;
2. a second synthetic `INTERNAL_ENDPOINT` service with a different service ID and registered adapter executes through the same generic path;
3. an unregistered service remains rejected;
4. a registered internal endpoint without an adapter remains rejected;
5. an adapter path outside the organization repository root is rejected;
6. adapter execution failure remains fail-closed;
7. boundary-local diagnostic/control behavior is unchanged.
